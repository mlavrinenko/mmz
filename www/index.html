mmz

memoized command runner

Prefix any command with mmz. When the matched rule's declared inputs are byte-for-byte unchanged since the command last succeeded, mmz skips it and exits 0. Otherwise it runs, streams output, and records the result.

Not a build system: no task graph, no artifact replay, no remote cache. One question per run — is this rule's work still done?

Install

cargo install mmz

Or grab a binary from the latest release.

Usage

mmz --init            # write a starter .mmz/config.yaml
mmz cargo test        # skipped when the declared inputs are unchanged
mmz --status          # show each rule's freshness and record age
mmz --status=json     # the same, with inputs and hashes, for jq
mmz --is-fresh -- cmd # exit 0 if cmd's rule is fresh; runs nothing (gate hooks)
mmz --is-fresh --tag t # gate only rules tagged t, instead of the whole manifest
mmz --prune           # drop cache records whose rule no longer exists
mmz --schema          # print the config JSON Schema

mmz fails closed: it errors when no manifest is found, the manifest is invalid, no rule matches, or a matched rule has no inputs. Relax the last two per project with the strict list.

Inputs are declared as named scopes of globs. Git-ignored paths are skipped by default, so a scope naming a build artifact would expand to nothing and its rule would report fresh forever. Spell that one scope as an object to opt it out — every sibling scope keeps filtering:

scopes:
  src: ["src/**"]              # inherits the default
  lcov:
    gitignore: false           # this scope only
    globs: ["target/coverage/lcov.info"]

A scope can only name whole files, so a rule depending on part of one has to hash all of it. A probes: entry closes that gap: its run line is executed, its stdout is hashed, and inputs: names the probe exactly as it names a scope:

probes:
  fmt-recipe:
    run: just --dump --dump-format json | jq -e -c '.recipes["fmt-check"]'

commands:
  - name: just fmt-check
    inputs: [rust, fmt-recipe]

Weigh the trade first: a wrong scope costs time, a wrong probe can lie. A probe that exits non-zero, cannot be spawned, or (without allow_empty: true) prints nothing is a hard error naming the probe — mmz exits 6, consumes no output and writes no record, so a failed command never reaches the hasher. Content correctness and determinism stay the manifest author's: assert the shape inside the probe (the jq -e above) so a bad shape becomes a non-zero exit. mmz does not validate meaning. Each probe is resolved once per invocation, however many rules name it.

A rule may also declare the artifacts its run produces. It is fresh only while its inputs hash the same and every declared output exists, so a cargo clean between two runs voids the record instead of leaving it fresh with nothing to show for it. Existence only — outputs are literal paths, stat-ed rather than walked, so the gitignore filter never applies to them:

commands:
  - name: just cover
    inputs: [rust]
    outputs:
      - target/coverage/lcov.info

A run that exits 0 without producing a declared output is a hard error (exit 5): mmz names the missing path and writes no record, rather than leaving a rule that quietly never hits again.
